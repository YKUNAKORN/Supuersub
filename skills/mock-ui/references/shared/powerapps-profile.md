# Power Apps profile: what a canvas screen can reproduce

<!-- Synchronised copy. The master lives in the plugin repository's shared folder and
     is copied into each skill that needs it. Edit the master, never this copy. -->

Use this file under the `power-apps` target. It says which design decisions the
`create-app` skill can turn into a working canvas screen, and which it cannot.

**Derived, not invented.** Every statement below comes from the `create-app` catalog,
`controls.yaml` (`catalog_updated: "2026-09-10"`, `studio_version_tested: unknown`), and
names the catalog key it came from in the form `catalog: <key>`. When the catalog
changes, this file is regenerated by hand from it and a unit test fails until every
`impossible_css` id is covered here.

**Absence is not evidence.** The catalog records positive results only. Anything not
listed here is *unverified*: not proven impossible, not proven possible. Say so; never
present it as either.

## 1. Controls with confirmed properties

Evidence levels are the catalog's own: `studio-tested` (pasted into Studio),
`example-file` (seen working in a bundled example).

Every control below also accepts `X, Y, Width, Height, Fill, Visible`.
catalog: `universal_properties`

## 2. What design tokens map to

| `DESIGN.md` token | Power Apps property | Reproducible on | Source key |
|---|---|---|---|
| component `backgroundColor` | `Fill` | every control | catalog: `universal_properties` |
| component `textColor` | `Color` | Label, Button, Icon, TextInput, DropDown | catalog: `controls[*].properties_confirmed` |
| component `rounded` | `RadiusTopLeft` … `RadiusBottomRight` | Button, GroupContainer, TextInput (not Rectangle) | catalog: `controls[Button\|GroupContainer\|TextInput].properties_confirmed` |
| component `borderColor` / `border` | `BorderColor`, `BorderThickness` | Button, GroupContainer, TextInput, DropDown | catalog: `controls[*].properties_confirmed` |
| component `height`, `width`, `size` | `Height`, `Width` | every control | catalog: `universal_properties` |
| typography `fontFamily` | `Font` | Label (Button: example-file only) | catalog: `controls[Label].properties_confirmed` |
| typography `fontSize` | `Size` | Label, TextInput, DropDown (Button: example-file only) | catalog: `controls[Label].properties_confirmed` |
| typography `fontWeight` | `FontWeight` | Label only; on Button it is unverified | catalog: `controls[Label].properties_confirmed` |
| `-hover` component variant | `HoverFill`, `HoverColor`, `HoverBorderColor` | Button, Icon | catalog: `controls[Button\|Icon].properties_confirmed` |
| `-active` / `-pressed` variant | `PressedFill`, `PressedColor`, `PressedBorderColor` | Button, Icon | catalog: `controls[Button\|Icon].properties_confirmed` |
| `-disabled` variant | `DisabledFill`, `DisabledColor`, `DisabledBorderColor` | Button, Icon | catalog: `controls[Button\|Icon].properties_confirmed` |
| `-focus` variant | `FocusedBorderThickness` | Button, Icon | catalog: `controls[Button\|Icon].properties_confirmed` |

No catalog key covers these token properties, so on a canvas they are **unverified**:

- `padding`: no padding property is catalogued. `create-app` reproduces padding by
  placing children at an offset inside a container, which works, but it is geometry, not
  a property.
- `lineHeight` and `letterSpacing`: no Label property for either is catalogued. Keep
  `letterSpacing` at `0px` under this target, and treat `lineHeight` as a guide to
  control height, not something the screen will reproduce exactly.

## 3. Controls nobody has tried yet

catalog: `unattempted_controls`

Timer, Slider, DatePicker, Toggle, ComboBox, Gallery, DataTable, PDFViewer, Camera,
Barcode.

A design may still call for one of these (a date field, a switch, a repeating list), but
say that the control is unattempted. `create-app` will hand over an isolated paste test
for it rather than a guess.

## 4. Effects the catalog rules out, and what replaces them

These have no confirmed Power Fx equivalent. Under the `power-apps` target, do not
design with them. When the user asks for one, say plainly that the canvas cannot
reproduce it and offer the substitute.

### box-shadow
catalog: `impossible_css[id=box-shadow]`. No confirmed equivalent, on hover or otherwise.
Substitute (the catalog has none): show elevation with a surface colour change or a 1px
border in a hairline colour.

### backdrop-blur
catalog: `impossible_css[id=backdrop-blur]`. No confirmed equivalent. Substitute (the
catalog has none): an opaque surface colour.

### css-transition
catalog: `impossible_css[id=css-transition]`. Transitions and animations have no
confirmed equivalent. Substitute (the catalog has none): instant state changes through
the Hover, Pressed and Disabled properties a Button already has.

### group-hover
catalog: `impossible_css[id=group-hover]`. A child changing when its parent is hovered:
Label and Button do not share hover state. A workaround through formulas exists but is
"possible but not yet confirmed". Substitute (the catalog has none): put the hover
effect on the Button itself.

### border-left-only
catalog: `impossible_css[id=border-left-only]`. One-sided borders are not supported
directly. Substitute, from the catalog: "A thin Rectangle positioned along the edge."

### non-segoe-font
catalog: `impossible_css[id=non-segoe-font]`. Whether a font other than
`Font.'Segoe UI'` renders on the target machine is unverified either way. Substitute
(the catalog has none): set `fontFamily` to `Segoe UI` first in the stack, or keep the
brand face and mark it unverified.

## 5. How to use this profile when designing

- Pick colours, sizes and radii freely: `Fill`, `Color`, `Size` and `Radius*` take any
  value.
- Describe hover, pressed, disabled and focus states only for buttons and icons.
- Keep shadows, blur, transitions and one-sided borders out of the design. Where the
  user wanted one, record it in `## Known Gaps` with its substitute.
- Name anything unverified as unverified. Never upgrade it.
